faultclip

When a command fails, the next agent should see why

A small, dependency-free library that keeps the lines explaining a failure when tool output must fit a fixed character budget.

The problem

The line that explains a failure is usually the line that gets cut

Agent tools often shorten each tool result before a later agent reads it, and the simplest way is to keep the first few hundred characters. For a failed command, the decisive line usually sits at the end of a long traceback or test log.

Algorithm
What gets kept, in priority order


  1. Output that already fits the budget is returned unchanged.
    2. 

  2. One pass over the lines records the first error line, the line before it, the last error line, the last line that names an error, and the last two non-empty lines.
    3. 

  3. The chosen lines are ranked: the last named error first, then the first error and the line before it, then the final lines.
    4. 

  4. Each line gets space in that order, and every line still to come keeps a minimum of 80 characters in reserve. A very long error line is cut around its first error word, and no cut splits an emoji.
    5. 

  5. The kept lines go back into their original order and are joined with .... The result never exceeds the budget.


Tradeoffs
What it costs and what it leaves alone
    

  • Same budget, different text. Nothing gets longer. Output from a command that succeeded is cut the old way.
    • 

  • Heuristic, not a parser. It reads lines, not language-specific error formats. That keeps it small and fast on a million-line log, and it means some errors with no error word are missed.
    • 

  • Priority over completeness. One decisive line is kept at the cost of context in the middle. The blind test below checks that this is a good trade.


Benchmark method
How the results are measured
    

  • Data. Failed tool results from two public sets of coding-agent sessions at pinned revisions. The development set has 11 repositories. The unseen set takes one session from each of 208 other repositories, chosen by a fixed seeded rule.
    • 

  • Key line. The last line of the full output that names an error, ignoring source-file paths and command markers, with decoration such as ===== stripped and cut to 120 characters.
    • 

  • Kept. A method keeps the key line when its 600 characters contain it. The table here counts it inside the failed result itself. Counting it anywhere in a whole digest gives slightly higher figures and the same ranking.
    • 

  • Honest scope. The key-line measure is close to what the method selects, so the blind test is the stronger evidence of usefulness.


Decisions
Why it works this way
Same budget, better selection
A larger limit would also keep the error, but it makes every digest longer for every reader. This change spends the same 600 characters differently, and only on failures.
The smallest change that worked
Only failed results change. Output from commands that succeeded keeps the plain first-600-characters cut, so the change touches the one place where the decisive line is known to go missing.
A count is not an error name
Lines like 1 failed and file names like reproduce_error.py cannot take the slot reserved for the line that names the error.
Every chosen line keeps room
Each line reserves space for the lines after it, so one very long line cannot crowd out the final lines.
Linear, with little memory
A single pass keeps a few line positions, so a million-line log needs no line array.
Safe text boundaries
The result never exceeds the budget in UTF-16 units and never splits an emoji or other surrogate pair.

The unseen blind test includes only cases where the new digest kept the error, and its control group is small (8 items, 3 with a banner as the key line).


Limits
Known gaps
  • A heuristic picks the named line. A file name followed by :  with an error word in it counts as a name.
  • Go compile errors with no error word, such as file.go:12: undefined, are not treated as error lines.
  • The 60-case blind test informed development, and half of it comes from one repository.
  • One model wrote the notes and one graded them.
  • The control groups are too small to prove there is no harm.
